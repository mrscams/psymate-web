## Le produit en trois phrases

**PsyMate** est une application web multi-praticiens (psychologues, psychiatres, coachs) pour suivre l'évolution d'un patient : chaque fait est une **entrée** datée et versionnée (note, événement, situation, ressenti, séance, médicament), chaque relation est un **lien** typé de première classe, et les vues (vue d'ensemble, timeline, graphe, recherche) rendent les motifs visibles. V1 sans IA ; V2 avec suggestions de liens par l'IA, conçue dès maintenant. Un annuaire public (psymate.com) permet aux visiteurs de trouver et contacter un praticien **dont le dossier professionnel a été vérifié par un administrateur**.

## Décisions prises (ne pas rediscuter sans raison)

- **Produit PsyMate** (G Q1) : package Java `com.psymate`, domaine psymate.com, constante i18n `app.name = PsyMate`.
- Angular + Spring Boot (monolithe modulaire Spring Modulith) + PostgreSQL 16 ; Maven avec wrapper ; deux dépôts privés sur le compte GitHub `mrscams` : `psymate-api` et `psymate-web` (G Q2), pas de licence open source ; contrat OpenAPI versionné par tag.
- **Versions (27 octobre 2026)** : **Spring Boot 4.1** (Spring Framework 7, Jakarta EE 11, Jackson 3), **Spring Modulith 2.1.2** (ligne 2.1, alignée sur Boot 4.1), Java 21, **Angular 22** (Material 22, zoneless, Signal Forms), Node 22, PostgreSQL 16. Choisies parce que ce sont les lignes stables et supportées au démarrage : Spring Boot 3.5 est hors support OSS depuis le 30 juin 2026, Angular 20 sort du support fin novembre 2026, et Angular passe à une majeure par an (v23 en juin 2027, support deux ans), donc aucune montée majeure forcée pendant M0–M7. Toute montée de version est une PR dédiée.
- Base locale `psymate`, utilisateur `psymate`, rôle applicatif `psymate_app` créé par l'init du conteneur ; Flyway pose les `REVOKE` sur les tables append-only (G Q9).
- Neuf modules : identity (avec sous-domaines `preferences`, `verification`, `admin`), patients, vocabulary, clinical, linking, search, overview, events, directory ; `ai` réservé à la V2, `companion` réservé pour le compagnon patient (tous deux vides). **`identity.admin` ne dépend d'aucun module clinique** (règle ArchUnit) : l'administration ne voit jamais un patient. Pas de module `scheduling` : l'agenda Google est hors V1 (G Q25).
- Toute entrée appartient à une **séance** (séance d'accueil créée avec le patient ; contact hors rendez-vous = séance « contact »). Pas de fonction « déplacer », la séance est un champ modifiable. Durée de séance proposée par défaut : 60 minutes (préférence).
- Modèle hybride d'entrées (table commune + table de détail par type). Corrections = nouvelle version ; **règle de grâce** 5 minutes (même auteur, pas de lien, pas de version) sans version. Suppression = archivage.
- Liens = table `link` avec type, provenance (`manual`, `ai_suggested`, `ai_confirmed`), statut (`proposed`, `accepted`, `rejected`, `superseded`) ; rejets conservés. Graphe = CTE récursives SQL, pas de base graphe séparée. Matrice des types de liens E5.3 conservée (G Q12).
- Émotions : vocabulaire global (Plutchik étendu, les 29 codes de E5.2 livrés tels quels, G Q11) + émotions **custom** par praticien, tracées, famille obligatoire ; fusion de deux émotions custom en V1, promotion en V2 (G Q8) ; `valence` et `arousal` nullables en V1, remplis avant la V2. Tags, versions et drapeaux de patient : oui (G Q7).
- Temps : `occurred_from/to`, précision (exact, jour, mois, année, période, phase de vie), `recorded_at`.
- Hooks V2 dès la V1 : outbox Modulith, tables vides `entry_embedding` (pgvector), `entry_chunk`, `ai_feedback`, colonne `visibility`.
- Annuaire public : professions psychologue / psychiatre / **coach** (libellé « Coach » ou « Coach mental »), profil public opt-in, module `directory` en lecture seule, endpoints `/api/public/directory…`. Spécialités et publics : **liste fermée** administrable, pas de saisie libre (G Q15). Le formulaire de contact de la fiche est un **relais e-mail** (pas de messagerie intégrée en V1 ; trace technique 30 jours pour l'anti-spam). Pas de pied de page « numéros d'urgence » (G Q20). Signalements de l'annuaire : V1.1 (G Q26).
- **Vue d'ensemble à deux niveaux** (25 octobre) : vue **simple « Récit »** par défaut (résumé rédigé par règles, tendance expliquée en une phrase et vrais ressentis, dernière séance entière) et vue **complète** ; bascule « Vue : Simple · Complète » à droite des onglets, sélecteur 30 j / 90 j / 1 an dans les deux. La V3 « Préparer la séance » est abandonnée.
- **Préférences par compte** (25 octobre) : chaque bascule visible (vue, fenêtre, regroupement timeline, thème…) enregistre immédiatement une clé de `practitioner.preferences` JSONB via `PATCH /api/me/preferences` ; valable sur tous les appareils ; `localStorage` n'est qu'un cache. Défauts selon la profession (`coach` → « client », type médicament masqué) ; `locale` fr par défaut.
- **Inscription ouverte** (G Q21) : pas de code d'invitation ; les seuls freins sont la confirmation d'e-mail et les limites de taux. Le déploiement 5 → 20 → 50 praticiens se fait par invitation informelle.
- **Vérification des praticiens** (25 octobre) : inscription avec profession, n° pro, téléphone, adresse du cabinet (ou visio uniquement) → e-mail confirmé → **dossier professionnel** (diplôme et pièce d'identité obligatoires pour toutes les professions, attestation ADELI/RPPS recommandée : G Q14) → validation par un **administrateur** (approuver / demander un complément / refuser et suspendre, message obligatoire, décision append-only, e-mail). **Outil clinique ouvert dès l'e-mail confirmé** ; annuaire, badge « Profil vérifié » et contact public bloqués jusqu'à l'approbation. Alternative « tout bloquer avant validation » notée (ADR-12), à réévaluer si l'inscription ouverte amène trop de comptes non qualifiés. Justificatifs chiffrés hors base (disque local en dev, stockage de bêta décidé avec l'étude hébergement : G Q17), URL signées 5 min, journal d'accès, purge 90 jours après décision. Comptes, suspension manuelle, journal (`security_event` + vue `admin_journal_v`, G Q29), recours et vocabulaire de l'annuaire : tâche **M1-14b** (G Q27, Q28). Export d'un compte refusé ou suspendu : `export_job`, lien 7 jours, dans M6-05 (G Q18).
- Sécurité des comptes : sessions 12 h, 30 jours avec « rester connecté » (G Q6) ; 2FA TOTP optionnelle pour les praticiens, **obligatoire pour les administrateurs** ; verrouillage 15 min après 5 échecs ; aucune énumération de comptes ; journal `security_event` ; limitation de taux avec Bucket4j (G Q24). Premier administrateur `hushan@gmail.com` créé par `make admin` (G Q5). E-mails : `test@gmail.com` via Mailpit en dev, `noreply@psymate.com` en production, fournisseur SMTP choisi avec l'étude hébergement (G Q4).
- Français d'abord (G Q23) : structure i18n conservée, fichiers EN non bloquants.
- Capture rapide : barre de commande (`anx 8 n'a pas dormi > entretien`) avec aperçu, formulaire guidé en secours.
- Palette **Nordique** : cobalt #3A63C2, neutres gris-bleu (#EEF1F6, #D6DCE6, #1E2633, #5A6679), lavande #8B7BD6 réservée aux ressentis ; types d'entrées note #7F8EA8, événement #3A63C2, situation #2F4F73, séance #3E8E7E, médicament #B07A2A ; barre d'administration sombre #1E2633. Jamais de rouge sur un patient ou une émotion. Couleurs des familles d'émotions conservées (G Q13).
- Kafka : pas en V1 ; outbox interne d'abord, Kafka seulement si un consommateur sort du monolithe (laboratoire possible après M4).
- **Compagnon patient — réservé, non développé** (25 octobre, A11 / B9 / C7) : idée d'une application mobile (React Native pressenti, comparaison avec Capacitor + Angular à faire) où le patient garde ses ressentis et événements sur son téléphone et les **envoie en un lot d'un geste avant la séance** ; le praticien les intègre à la séance qu'il ouvre. Exercices = rappels purs. Pas de temps réel, pas de compte patient (appairage par code), pseudonymisation par défaut, numéros d'urgence visibles. **En V1, seuls les ancrages existent** : `entry.author_type` (toujours `practitioner`), `entry.submission_id` (toujours `NULL`), contrainte `ck_entry_session_required`, tables vides `patient_device` et `patient_submission`, package `companion` vide, `authorType` en lecture dans les DTO. Étude à écrire après M4 ; aucune tâche avant.
- Hors périmètre de ces études : hébergement, chiffrement, RGPD, sauvegardes, mineurs et consentement (étude séparée après le backend V1, préparée par M7-06 : G Q16, Q19). Le compagnon ne crée pas d'obligation réglementaire nouvelle, il ajoute du volume et du contenu plus intime aux données déjà de santé.
