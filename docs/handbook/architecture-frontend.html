Architecture frontend : comment on construit psymate-web

Ce document dit comment le frontend Angular est organisé, pourquoi ces choix, et quelles règles chaque tâche web (et chaque agent) suit. Il s'appuie sur les décisions déjà prises (C « Décisions d'outillage », C3, B7, G) et sur ce que le backend expose réellement (docs/contract/openapi.yaml, tag contract-v0.11.0). Il ne remplace ni les fiches d'écran (docs/design/) ni le runbook des lots (document H, à écrire) : il est la couche du milieu, « la façon de faire ».

1 · Principes : le miroir du backend

Un contexte = une feature

Le backend est un monolithe modulaire (Spring Modulith) : identity, patients, clinical, linking, search, overview, directory. Le frontend reprend le même découpage en features Angular lazy, avec les mêmes frontières : une feature ne touche pas l'intérieur d'une autre.

Le contrat est la seule porte

Le frontend ne connaît du backend que openapi.yaml à un tag. Le client TypeScript est généré, jamais écrit à la main, jamais modifié. Une route qui n'est pas dans le contrat n'existe pas pour le web.

Signaux partout, zone nulle part

Application zoneless, composants standalone OnPush, état dans des SignalStores (@ngrx/signals), formulaires en Signal Forms. Pas de Subject maison, pas de BehaviorSubject comme store, RxJS limité aux flux HTTP et aux événements DOM.

Un écran = une fiche

Chaque route a sa fiche docs/design/NN-*.md : route, API, structure, critères d'acceptation. Le code ne contient aucune décision fonctionnelle qui ne soit pas dans une fiche, B ou G.

Trois états toujours

Tout bloc qui charge des données a un état vide, chargement, erreur, rendus par le composant partagé shared/ui/state (planche 29). Pas de *ngIf="data" silencieux.

Rien en dur

Pas de couleur hexadécimale dans un composant (tokens CSS), pas de texte non traduit ($localize), pas d'URL d'API écrite à la main (client généré), pas de secret.

2 · Les six couches (du pixel à la requête)

Chaque feature est traversée par la même pile. Une couche ne parle qu'à celle du dessous. C'est ce qui rend le code lisible : on sait toujours où chercher.

1 · Pages (routées)Composant « intelligent » d'une route. Lit le store, orchestre, ne contient presque pas de HTML métier. Un fichier par route.features/patients/pages/patient-list.page.ts
▼ inputs / outputs (signals)
2 · Composants UI« Bêtes » : input(), output(), aucun service injecté sauf i18n/thème. Réutilisables, testables sans store. Les composants transverses vivent dans shared/ui.features/patients/ui/patient-row.component.ts
shared/ui/state/state.component.ts
▼ signals en lecture, méthodes en écriture
3 · Store (SignalStore)État de la feature : données serveur, filtres, sélection, statut de chargement. Méthodes = cas d'usage (load, archive, startSession). Un store par feature, parfois un par écran lourd (timeline).features/patients/data/patient.store.ts
▼ appels typés, Promises ou Observables courts
4 · Service de donnéesSeul endroit qui importe le client généré. Traduit les DTO en modèles de vue si besoin, assemble plusieurs appels, applique la pagination par curseur. Aucune logique d'affichage.features/patients/data/patient.api.ts
▼ méthodes générées, un fichier par tag OpenAPI
5 · Client généréopenapi-generator (typescript-angular) depuis docs/contract/openapi.yaml. Regénéré par pnpm contract:pull, commité, jamais édité.src/app/api/** (généré)
▼ HttpClient + intercepteurs
6 · TransportIntercepteurs dans core/http : cookie de session (withCredentials), erreurs application/problem+json, 401 → connexion, 403 d'état → redirections, 429 → Retry-After, hors ligne. Proxy /api → :8080 en dev.core/http/*.interceptor.ts
Pourquoi pas plus simple ? Sans la couche 4, le store importe le client généré et chaque régénération du contrat casse vingt fichiers. Sans la couche 3, l'état se disperse dans les composants et deux onglets ne se parlent plus. Six couches, c'est le minimum pour qu'une feature se lise de haut en bas.

5 · Frontières : qui a le droit d'importer qui

La même discipline que ApplicationModules.verify() côté API, vérifiée par ESLint (eslint-plugin-boundaries ou import/no-restricted-paths) et par un test qui fait échouer la CI sur un import interdit.

Ce que « index.ts public » veut dire. Une feature expose au plus : ses routes, un store si un autre écran en a besoin (ex. PatientShellStore), des types de vue. Tout le reste est interne. Si deux features ont besoin du même composant, il descend dans shared/ui par une tâche séparée (fiche 00), jamais par un import croisé.

6 · Communication avec le backend

6.1 Le contrat d'abord

1psymate-api taguecontract-vX.Y.Z après une vague ; springdoc génère openapi.yaml, la CI vérifie qu'il est à jour
2CONTRACT_TAGune PR d'une ligne côté web change le tag épinglé
3pnpm contract:pullcopie openapi.yaml au tag dans docs/contract, lance openapi-generator → src/app/api
4Compilationun champ renommé casse le build là où il est utilisé : c'est voulu
5Services de donnéesseuls fichiers à adapter ; les stores et les pages ne bougent pas si le modèle de vue tient
Générateur
@openapitools/openapi-generator-cli, générateur typescript-angular, version figée dans package.json, options : withInterfaces, stringEnums, supportsES6, un service par tag OpenAPI (Authentification, Patients, Entrées, Chronologie…).
Où il vit
src/app/api/, commité (diff lisible en PR), en-tête « généré, ne pas éditer », exclu de Prettier et de la couverture.
Règle de PR
Une PR qui change CONTRACT_TAG ne contient que la régénération et les adaptations des *.api.ts. Jamais mélangée à une feature.

6.2 Le cycle d'une requête (exemple : clôturer la séance)

1Utilisateurclique « Clôturer » dans l'en-tête patient (ou raccourci)
2Page / composantappelle shell.closeSession({durationMin, summary})
3PatientShellStorepasse status = 'saving', appelle le service de données
4session.api.tssessionsApi.closeSession(id, body) (client généré)
5Intercepteurscookie joint ; en cas d'erreur, problem+json → ApiProblem typé
6APIPOST /api/sessions/{id}/close → 200 SessionDto, ou 409 / 422
7StorepatchState : séance courante = null, dernière séance = réponse ; status = 'idle'
8Vueles signaux changent, l'en-tête se redessine (zoneless : rien d'autre ne se recalcule)

6.3 Session, sécurité, erreurs

Session par cookie, pas de jeton

Le backend pose un cookie HttpOnly; Secure; SameSite=Lax à POST /api/auth/login (12 h, 30 j avec « rester connecté », G Q6). Le frontend n'a aucun jeton à stocker : withCredentials: true sur HttpClient, proxy /api → :8080 en dev (même origine), même domaine en production. CSRF : désactivé côté API (JSON seulement) ; le frontend n'envoie donc pas de jeton CSRF, mais ne fait jamais de formulaire HTML natif vers l'API.

Au démarrage : GET /api/auth/me → SessionStore (id, displayName, profession, verificationStatus, role, twoFactorEnabled, passwordChangeRequired, v0.10.0+). 401 → pas de session → routes publiques seulement.

Une erreur = un objet typé

Toute réponse d'erreur est application/problem+json : { status, code, detail, errors[{field, code, message}], retryAfter? }. L'intercepteur la transforme en ApiProblem ; les stores ne voient jamais un HttpErrorResponse brut. shared/forms relie errors[] aux champs d'un formulaire par field.

export interface ApiProblem {
  status: number;          // 401, 403, 409, 422, 423, 429, 5xx
  code: string;            // UNAUTHENTICATED, VALIDATION_FAILED, LINK_EXISTS…
  detail?: string;
  errors?: { field: string; code: string; message: string }[];
  retryAfterSeconds?: number;   // 423, 429
  extra?: Record<string, unknown>; // existingLinkId, usedByPublishedProfiles…
}

401
UNAUTHENTICATED

403
EMAIL_NOT_CONFIRMED · ACCOUNT_SUSPENDED · PASSWORD_CHANGE_REQUIRED · TWO_FACTOR_REQUIRED · ADMIN_ROLE_REQUIRED

403

404
NOT_FOUND
Store : état vide/erreur selon le contexte
409
LINK_EXISTS, EXPORT_IN_PROGRESS, VOCABULARY_IN_USE…

422
VALIDATION_FAILED + errors[]

423

429

Intercepteur : toast « réessayez dans N s », la saisie est conservée ; aucun rejeu automatique sauf GET idempotent, une fois
0 / 5xx
hors ligne, INTERNAL_ERROR
Intercepteur : bandeau « Connexion perdue · brouillons conservés » / état erreur avec « Réessayer »

6.5 Conventions de données à respecter côté web

Pagination par curseur

?cursor=&limit=, réponse { items, nextCursor }. Le store garde items + nextCursor ; « charger plus » concatène. Exceptions : annuaire public et recherche (page / totalPages).

Dates

UTC ISO 8601 en transit ; affichage dans le fuseau du praticien via Intl. Précision d'une entrée (exact | day | month | year | period | life_phase) → un seul formatOccurred() dans shared/util.

Versions et grâce

Corriger une entrée = PATCH /api/entries/{id} avec reason ; dans la fenêtre de grâce (1 h 15, G Q31) le serveur modifie la v1 sans en créer. Le web affiche l'historique en lecture seule ; pas de « restaurer une version ».

Préférences

PATCH /api/me/preferences (merge RFC 7396) : chaque bascule visible écrit sa clé, de façon optimiste, repli sur la valeur serveur en cas d'erreur ; localStorage.prefs n'est qu'un cache de démarrage.

Projections

Vue d'ensemble et recherche sont des projections alimentées par événements : après une écriture, le web relit (GET …/overview) au lieu de recalculer localement ; stale → lien « Recalculer ».

Réserves (A11)

authorType est lu, jamais envoyé ; les composants gardent la place du marqueur « rapporté par le patient » sans le dessiner. Aucun écran ne suppose un « compagnon ».

// features/patients/data/patient.store.ts — squelette type
export const PatientStore = signalStore(
  { providedIn: 'root' },
  withState({ items: [] as PatientRow[], nextCursor: null as string | null,
              filter: '', status: 'idle' as Status, problem: null as ApiProblem | null }),
  withComputed(({ items, filter }) => ({
    visible: computed(() => filterByName(items(), filter())),
  })),
  withMethods((store, api = inject(PatientApi)) => ({
    async load() {
      patchState(store, { status: 'loading', problem: null });
      try {
        const page = await api.list({ cursor: null });
        patchState(store, { items: page.items, nextCursor: page.nextCursor, status: 'idle' });
      } catch (e) { patchState(store, { status: 'error', problem: asProblem(e) }); }
    },
    async archive(id: string) { /* optimiste : retire, appelle api.archive, remet si échec */ },
  })),
);
Lisibilité : un store se lit comme une liste de cas d'usage. Un composant ne contient jamais http.get, jamais subscribe sur une requête, jamais de transformation de DTO.

9 · UI, thème, i18n, accessibilité

Angular Material M3 + CDK, et seulement deux composants maison

Material pour tout ce qui existe (boutons, champs, chips, dialogues, menus, onglets, virtual scroll CDK, overlays). Maison : la timeline et la barre de commande (B7). Cytoscape pour le graphe, ECharts pour la courbe, tous deux chargés en @defer pour ne pas peser sur le bundle initial.

Tokens, pas de couleur en dur

src/theme/tokens.css = les variables de l'étude couleurs (§8), lues par Material (thème M3 construit dessus), par les composants maison, par Cytoscape et ECharts au démarrage et à chaque changement de data-theme. ESLint no-hardcoded-color + test de contraste en CI. Lavande réservée au ressenti ; jamais de rouge sur un patient.

Français d'abord

$localize partout, messages.fr.xlf complet à chaque tâche, EN non bloquant (G Q23). Pluriels ICU. Le libellé « patient » devient « client » via le contexte subject quand vocabulary.subjectLabel = client ; les données saisies ne sont jamais traduites.

Accessibilité comme critère, pas comme finition

Landmarks, focus visible, ordre de tabulation, tout au clavier, panneaux role="dialog" avec piège de focus, liste équivalente pour le graphe, zoom 200 %, prefers-reduced-motion. axe-core dans chaque e2e ; zéro violation « serious » est un critère de fin de tâche.

Formulaires

Signal Forms (stables en Angular 22) pour l'éditeur d'entrée, la fiche patient, le profil public, l'inscription ; validation synchrone côté client pour les règles simples (longueur, requis, ≥ 12 caractères), le serveur reste juge : les errors[] d'un 422 sont reliés aux champs par shared/forms/applyProblem(). Un formulaire ne duplique jamais une règle métier qui vit dans le backend (matrice des liens, complétude du dossier).

11 · Les 14 règles (à recopier dans CLAUDE.md du dépôt web)

1
Une feature par contexte backend, lazy, avec un index.ts public.Aucun import de l'intérieur d'une autre feature ; admin n'importe jamais une feature patient.
2
Le client src/app/api est généré au tag CONTRACT_TAG et jamais édité.Seuls les *.api.ts l'importent. Un changement de tag = une PR dédiée.
3
Six couches, chacune ne parle qu'à celle du dessous.Page → UI → Store → Service de données → Client → Transport.
4
Standalone, zoneless, OnPush, signaux.Pas de store RxJS maison ; RxJS seulement pour HTTP et événements DOM.
5
L'état serveur vit dans un SignalStore, l'état d'écran dans le composant, les préférences dans PreferencesStore.Jamais la même donnée à deux endroits.
6
Toute erreur HTTP devient un ApiProblem ; les codes 401/403 d'état et 429 sont traités par les intercepteurs, 409/422 par l'écran.Aucun composant ne voit un HttpErrorResponse.
7
Trois états par bloc de données, avec shared/ui/state.Vide, chargement, erreur ; critère de fin de tâche.
8
Les composants partagés (fiche 00) ne se modifient que par une tâche dédiée.Un écran qui en a besoin d'une variante ouvre une tâche, il ne forke pas.
9
Aucune couleur hexadécimale, aucun texte non $localize, aucune URL d'API écrite à la main.ESLint + test de contraste + revue.
10
Le serveur reste juge des règles métier.Le client valide la forme (requis, longueur) ; la matrice des liens, la grâce, la complétude viennent du backend.
11
Lecture après écriture pour les projections.Vue d'ensemble, recherche : on relit, on ne recalcule pas localement.
12
Chaque critère d'acceptation d'une fiche devient un test, et chaque flux de B3 un e2e contre l'API réelle.Pas de mock de la base ni du backend en e2e.
13
Versions figées dans package.json ; aucune dépendance sans l'annoncer dans la PR.Montée de version = PR dédiée (C « Versions »).
14
authorType en lecture seule, place réservée, jamais dessiné.Aucun écran ne suppose le compagnon patient (A11, B9).
